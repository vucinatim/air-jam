# Controller UI

Controller UI should feel like a game controller first and a webpage second.

The main failure mode is borrowing desktop web-app patterns for active gameplay surfaces.

## Gameplay Controller Rules

A game whose `inputModalities` include `'joystick'` always gets a landscape controller; the SDK applies it, so do not set orientation; lay it out with `GamepadLayout` from `@air-jam/sdk/ui`: the stick under the left thumb, the actions under the right in a square the same size, and only short status between them.

For active gameplay:

1. use an absolute `inset-0` root
2. avoid scroll
3. disable accidental text selection
4. use large touch targets
5. keep controls visually obvious and single-purpose
6. minimize text and dense hierarchy

## Sideways Controllers

A sideways phone is held like a gamepad, so its controls use the screen like one. Compose them in `GamepadLayout`:

1. the stick goes in `left` and the actions in `right`; both get the same square, so they carry the same weight and mirror each other about the centre, each centred in its thumb zone on one line
2. a single action fills its square; several actions share it as one cluster, as phone action games do, rather than starting a third column: the main action sits at the square's centre under the resting thumb at about half the square's width, each other action is about two thirds of the main one's size on a tight arc around its inner side (below, toward the centre, above) with the most used nearest, a rarely used utility goes smaller on the outer side, and every button stays inside the thumb zone
3. a button with a cooldown shows it on itself: a dark sweep over the icon that shrinks as it recovers, the seconds left when the wait is over a second, and full colour once it is ready again
4. buttons show icons, not words, drawn as one family: the same grid, the same stroke width with round caps and joins (or all filled), the same optical size of about half the button, one simple silhouette each and no detail finer than the stroke; judge them at real size on a phone
5. `center` holds only what a player reads at a glance: a round, a number, a word, a few icons; it never wraps into squeezed lines
6. a longer message goes in the header bar above the layout, or stays on the TV

```tsx
import { ControlButton, GamepadLayout, Stick } from "@air-jam/sdk/ui";

// Before: a big stick, a small button pushed to the edge, a sentence wrapping between them.
<div className="flex h-full items-center justify-between px-6">
  <Stick control={gameInput.move} className="size-56" />
  <p className="max-w-48 text-2xl">Splash! Back next round</p>
  <ControlButton control={gameInput.dash} className="size-28">Dash</ControlButton>
</div>

// After: equal mirrored thumbs, a glanceable centre, the sentence in the header.
<GamepadLayout
  left={<Stick control={gameInput.move} className="rounded-full bg-white/10" />}
  center={<span className="text-xs uppercase">Round 1</span>}
  right={<ControlButton control={gameInput.dash} className="rounded-full bg-sky-400">Dash</ControlButton>}
/>
```

## Lobby Rules

Lobby screens can be slightly more flexible, but should still prefer:

1. simple layout
2. large controls
3. minimal friction
4. scroll only when it actually helps the flow

## Interaction Rules

Avoid:

1. tiny toggles
2. multi-purpose buttons with unclear affordance
3. deeply nested control groups
4. layouts that assume precise pointer interaction

## Visual Rules

Prefer:

1. sparse game-like hierarchy
2. fluid layout over hard-coded widths and heights
3. obvious action grouping
4. strong contrast and immediate readability

Avoid:

1. card-heavy dashboard styling for active gameplay
2. emoji-as-icon UI
3. cluttered web-app chrome

## Icon Rule

For template and starter work, a practical split is:

1. a general UI and system icon pack for shell actions
2. a gameplay-oriented icon set for abilities, pickups, and status effects

Keep icon usage behind local wrappers where practical so the project can curate or replace icons later.

## Private player screens and word games

Keep secret words or cards in a per-controller map declared with
`createAirJamStore`'s `privateField`; read that phone's entry with
`useAirJamPrivateState`. The public store excludes this field and each phone
receives only its own entry. Test a reveal with `studio_press_phone`'s hold action.

A decision-model seat (Jev) answers choice questions only. Give model seats authored
candidate clues or answers as options; people can type freely into phone fields.
