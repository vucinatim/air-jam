# Input System

A game declares the controls each player has. Phones, agents and replays fill
those controls; the host reads them once per simulation step, with a fixed
meaning for each kind of control.

## Declare Controls

```ts
// src/game/contracts/input.ts
import {
  button,
  defineAirJamInput,
  stick,
  type AirJamInputValues,
} from "@air-jam/sdk/core";

export const shipInput = defineAirJamInput({
  move: stick(),
  fire: button("pressed"),
  boost: button("held"),
});

export type ShipInput = AirJamInputValues<typeof shipInput>;
```

Declare them once in `src/airjam.config.ts` with `defineAirJamGame` from `@air-jam/sdk/core`:

```ts
export const airjam = defineAirJamGame({
  // ...
  simulation: shipSimulation,
  input: shipInput,
});
```

## Control Kinds

| Kind                           | Declared as                      | A step reads                                                                               |
| ------------------------------ | -------------------------------- | ------------------------------------------------------------------------------------------ |
| Held button                    | `button("held")`                 | `true` while the button is down, and for at least one step after a tap shorter than a step |
| Pressed button                 | `button("pressed")`              | `true` for exactly one step per press                                                      |
| Axis                           | `axis()`                         | a number from -1 to 1                                                                      |
| Stick                          | `stick()`                        | `{ x, y }`, each from -1 to 1; `y` is down, like screen space                              |
| Stick that keeps its direction | `stick({ keepDirection: true })` | the last direction while the stick is centred, as in snake                                 |

Presses travel as a counter, so a tap between two network packets or two
simulation steps is never lost or doubled. Games never debounce or latch input
themselves.

## Read Controls In The Simulation

Input reaches a game only in its simulation steps:

```ts
export const shipSimulation = defineAirJamSimulation<Sim, ShipInput>({
  stepMs: 1000 / 60,
  create: () => createSim(),
  step: (sim, { input, players, dtSeconds }) => {
    for (const player of players) {
      const { move, fire, boost } = input(player.id);
      steer(sim, player.id, move, boost, dtSeconds);
      if (fire) shoot(sim, player.id);
    }
  },
});
```

`input(playerId)` always returns every control. A player who has sent nothing
yet reads as released and centred.

## Phone Controls

The SDK's phone controls fill the declared controls and send them; a game
never runs its own send loop.

```tsx
import { AxisButton, ControlButton, Stick } from "@air-jam/sdk/ui";

<Stick control={shipInput.move} className="size-48 rounded-full bg-zinc-900" />
<ControlButton control={shipInput.fire} className="bg-red-500 data-[active=true]:ring-2">
  Fire
</ControlButton>
```

1. `ControlButton` binds a button. Each touch, or Space and Enter while it has
   focus, is one press.
2. `AxisButton` holds an axis at a value while held, such as a paddle's up and
   down buttons. The latest held button wins.
3. `Stick` reads a drag anywhere inside it. `directions="4-way"` snaps it to a
   pad, `deadzone` keeps small offsets centred, and a function child draws the
   whole stick. It stays correct however the controller surface is rotated.

Every control sets `data-active` while held, so games style the held state
with their own classes. Controls release when the phone page loses focus.

The controller sends its controls once per display frame when they change, again
after joining, and on a slow keepalive. Nothing stamps input with a device
clock.

## Keyboards And Gamepads

Declare bindings for the controls and every keyboard layout and gamepad plays
as a local player, with no phone:

```ts
import {
  arrows,
  button,
  defineAirJamInput,
  defineAirJamInputBindings,
  stick,
  wasd,
} from "@air-jam/sdk/core";

export const shipInput = defineAirJamInput({
  move: stick(),
  fire: button("pressed"),
  boost: button("held"),
});

export const shipInputBindings = defineAirJamInputBindings(shipInput, {
  keyboard: [
    { move: wasd(), fire: "Space", boost: "ShiftLeft" },
    { move: arrows(), fire: "Enter", boost: "ShiftRight" },
  ],
  gamepad: { move: "leftStick", fire: "south", boost: "rightTrigger" },
});

// airjam.config.ts
defineAirJamGame({ input: shipInput, inputBindings: shipInputBindings, ... });
```

1. Each keyboard layout is one player; every connected gamepad is one more.
   Keys are `KeyboardEvent.code` values. A button binds one or more keys, an
   axis binds `keyAxis(negative, positive)`, and a stick binds `wasd()`,
   `arrows()` or `keyStick({ up, left, down, right })`. A binding for a
   control that isn't declared, or of the wrong kind, throws when declared.
2. Gamepad names follow the standard layout: `south`, `east`, `west`,
   `north`, `leftBumper`, `rightBumper`, `leftTrigger`, `rightTrigger`,
   `select`, `start`, stick presses and the d-pad for buttons;
   `leftStickX`/`Y` and `rightStickX`/`Y` for axes; `leftStick`, `rightStick`
   or `dpad` for sticks. Sticks get a small deadzone and stay y down.
3. A layout's first key, or a gamepad's first button or stick push, opens a
   seat: a preview phone named "Keyboard 1" or "Gamepad 1" that joins like any
   phone. Its own screen answers menus and lobby buttons; the keys or buttons
   drive play. Minimizing that phone keeps it playing; removing it frees the
   seat, and the next key opens a new one.
4. Keys and gamepads count only while the game page has focus, key repeats
   never press, and losing focus or unplugging a gamepad releases what it
   held. Keys aimed at the page's own buttons and fields stay theirs.

Local development's preview phones and Studio provide these seats; a page
with nobody to provide them leaves keys and gamepads alone. Game code never
listens to keys or polls gamepads itself.

A product framing a game offers its preview workspace's phones as that
game's seats by passing the game frame to `PreviewControllerWorkspace` as
`localPlayersGame`; `localPlayers={false}` offers none and closes the seats
it opened. The Arcade offers them only once a player turns keyboard and
gamepad players on.

A product framing its own phones launches each with
`createPreviewControllerLaunch` from `@air-jam/sdk/preview`, passing its
page's origin as `parentOrigin` and, for a seat, its label as `localSeat`. A
phone takes seat input and close requests only from its direct parent at that
origin, and answers only there; without `parentOrigin` that is the phone's own
origin, as the preview workspace launches it.

## Agents

Agents fill the same controls through leased participant control. They send
values: a button is `true` or `false`, an axis a number and a stick an
`{ x, y }`. A button going from `false` to `true` is one press; to press again,
send `false` and then `true`. The input description agents read comes from the
declaration.

## Input Log And Replays

Every host whose game declares a simulation keeps a version 2 input log,
from construction, in the browser as well as headless. It contains the real
seed, resolved initial settings, players joining and leaving, room state,
store actions applied between steps, controls when they change and accepted
settings updates. Each event carries the step it reached the game before.
Actions a step causes replay with the simulation and are not logged again.
`runtime.inputLog()` reads it locally; it throws while the simulation is
loading or when the game declares none.

The recorder retains the start of the match. It freezes before a step would
exceed 30 minutes of played game time or 16 MiB (the sum of each entry's JSON
length). A full log ends at the last whole step and excludes pending events.
`runtime.inputLogFull` reports this without changing the version 2 format.
Reload the game to start a new recording.

Agents use `readHostInputLog(request, observation.identity)` from
`@air-jam/sdk/runtime-control` through the existing host-agent channel. It
returns `{ status: "recorded", log, full }`, or `{ status: "not-replayable",
reason, message }`. Reasons are `no-simulation`, `loading`, `runtime-replaced`
and `host-unavailable`. A game without a simulation says:
"This game has no simulation, so its matches cannot be replayed; record a clip instead."
Reading needs no room grant. The first `input-log-read` request fixes a cut;
later pages read the same prefix while the match keeps playing.

Headless runs keep the log in their evidence. Running

```bash
airjam session run replay <run-id>
```

plays it on a fresh copy of the game, with no server or page, and reports
whether the replay ends where the run ended.
`replayAirJamInputLog(airjam.createHostRuntime, log)` from
`@air-jam/sdk/core` remains the run-to-completion form.

For playback, `await openAirJamReplay(airjam.createHostRuntime, log)` returns
`{ runtime, roomId, agent, stop, stepMs, ticks, tick, done, advance }`.
It stays paused between calls. `advance({ steps: 10 })` runs whole steps;
`advance({ ms: elapsed * speed })` carries fractions between calls, so a
caller can drive any speed per animation frame. Both return the current tick
and clamp at `ticks`. Reaching the end applies events after the final step
once, including on a recording with zero steps. Call `stop()` when finished.

There is no backward seek. Open a new replay and advance to the desired tick.
Each replay needs a fresh load of the same game source, in its own page or
headless process: game stores are module singletons and cannot share the load
with the live game or another replay. Exact replay also requires game code to
draw randomness from the step's seeded `random`.

## Common Issues

### A Control Does Nothing

1. Check the control is declared and passed to `defineAirJamGame({ input })`.
2. Read it in the simulation step; the host has no other way to read input.
3. Render phone controls inside `<airjam.Controller>`.

### A Tap Fires Twice Or Not At All

Use `button("pressed")` for one-shot actions, which then read `true` once per
press, and `button("held")` for actions that last while held.
